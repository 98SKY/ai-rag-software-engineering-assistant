# Technology Stack and Technology Selection

## 1. Introduction

The AI-Powered Software Engineering Assistant is implemented using a
combination of frontend, backend, database, vector-search, embedding,
and Large Language Model technologies.

The technology stack was selected to support the major requirements
of the system:

- Responsive web interface
- REST API development
- Document processing
- Vector embedding generation
- Semantic similarity search
- Retrieval-Augmented Generation
- Cloud and local vector storage
- LLM-based answer generation
- Experimental evaluation

The high-level technology architecture is:

```text
React + TypeScript
        |
        | REST API
        v
     FastAPI
        |
        +--------------------------+
        |                          |
        v                          v
     SQLite                  RAG Pipeline
                                   |
                     +-------------+-------------+
                     |                           |
                     v                           v
             Sentence Transformer          Vector Store
                                                |
                                      +---------+---------+
                                      |                   |
                                      v                   v
                                    FAISS              Astra DB
                                      |
                                      +---------+---------+
                                                |
                                                v
                                             Groq LLM
```

# 3. Frontend: React

The application frontend is developed using React.

React is responsible for building the interactive user interface of
the Software Engineering Assistant.

The frontend currently provides:

- Knowledge-base document listing
- Document upload
- Chat interface
- Question submission
- Generated-answer display
- Retrieved-source display
- Similarity information
- Retrieval and generation metrics
- Responsive layouts

The frontend is divided into reusable components such as:

```text
App
 |
 +-- AppLayout
 |
 +-- Header
 |
 +-- Sidebar
 |     |
 |     +-- DocumentUpload
 |     +-- DocumentList
 |            |
 |            +-- DocumentCard
 |
 +-- ChatPanel
       |
       +-- Conversation
       |      |
       |      +-- ChatMessage
       |      +-- SourceCard
       |      +-- RetrievalMetrics
       |      +-- ThinkingIndicator
       |
       +-- QuestionInput
```

This component-based architecture improves maintainability and keeps
presentation responsibilities separated.

---

# 4. Why React?

React was selected because the application requires a dynamic
interactive interface.

For example, the UI must update when:

```text
Document uploaded
        ↓
Knowledge Base updated

Question submitted
        ↓
Loading state displayed
        ↓
Answer received
        ↓
Conversation updated
```

React's component and state model is suitable for this interaction
pattern.

React also allows the frontend to be separated from the backend,
which makes the architecture easier to maintain and extend.

---

# 5. TypeScript

TypeScript is used as the frontend programming language.

TypeScript extends JavaScript with static type checking.

For example, the RAG API response is represented using interfaces:

```typescript
export interface AskResponse {
  question: string;
  answer: string;
  sources: SourceReference[];
  retrieval: RetrievalMetadata;
}
```

This provides compile-time checking between frontend components and
the expected API structure.

Benefits include:

- Better type safety
- Easier refactoring
- Improved IDE support
- Reduced runtime errors
- Clear API contracts

---

# 6. Vite

Vite is used as the frontend development and build tool.

Its responsibilities include:

- Starting the frontend development server
- TypeScript/React development workflow
- Fast development refresh
- Production frontend builds
- Environment-variable integration

The development frontend currently runs on:

```text
http://localhost:5173
```

The backend allows this origin through CORS during local development.

---

# 7. React Markdown

LLMs frequently return Markdown-formatted responses.

For example:

```markdown
The system uses:

- Apache Kafka
- Redis
- Kubernetes
```

Rendering this response as plain text would expose Markdown symbols
instead of formatted content.

React Markdown is therefore used to convert generated Markdown into
React-rendered content.

This improves readability for:

- Lists
- Bold text
- Paragraphs
- Inline code
- Code blocks

# 8. Backend: Python

The backend is implemented using Python 3.11.

Python was selected because the project contains significant
AI-related functionality.

The Python ecosystem provides direct support for:

- Sentence Transformers
- PyTorch
- FAISS
- NumPy
- Astra DB SDK
- LLM SDKs
- Document-processing libraries

Using Python therefore allows the API and AI pipeline to exist within
the same backend environment.

```text
POST /api/v1/documents/upload

GET  /api/v1/documents/{document_id}/chunks

POST /api/v1/ask
```

FastAPI coordinates the different services involved in the RAG
pipeline.

Conceptually:

```text
HTTP Request
     |
     v
FastAPI
     |
     +-- Document Service
     |
     +-- Embedding Service
     |
     +-- Retrieval Service
     |
     +-- RAG Service
     |
     +-- LLM Service
```

---

# 10. Why FastAPI?

FastAPI was selected because it integrates naturally with the Python
AI ecosystem.

Advantages for this project include:

- Python-native AI integration
- Type validation using Pydantic
- Automatic OpenAPI documentation
- Asynchronous endpoint support
- Lightweight REST API development
- Easy integration with SQLAlchemy
- Easy integration with ML libraries

The automatic API documentation is also useful during project
development and demonstration.

---

# 11. Why Not Use Spring Boot for the AI Backend?

Spring Boot could also be used to build the REST API.

However, this project uses Python because the primary research focus
is AI and Retrieval-Augmented Generation.

The major AI libraries used by the project are directly available in
Python:

```text
sentence-transformers
PyTorch
FAISS
NumPy
```

Using FastAPI avoids introducing an additional service boundary
between a Java backend and a separate Python AI service during the
prototype stage.

A larger production system could use an architecture such as:

```text
React
   |
   v
Spring Boot
   |
   v
Python AI/RAG Service
```

but that would introduce additional distributed-system complexity
that is not necessary for the current research objective.

# 12. SQLAlchemy

SQLAlchemy is used as the ORM layer.

It maps Python classes to relational database tables.

The current major entities are:

```text
Document

DocumentChunk
```

The relationship is approximately:

```text
Document
   |
   | 1
   |
   | N
   v
DocumentChunk
```

A single uploaded document can contain multiple chunks.

# 13. SQLite

SQLite is currently used as the relational metadata database.

It stores information such as:

```text
Document
--------
id
filename
stored_filename
content_type
size
characters_extracted
chunk_count
created_at
```

and:

```text
DocumentChunk
-------------
id
document_id
chunk_index
content
character_count
faiss_index
```

SQLite is not used as the primary semantic-search engine.

Its purpose is application metadata persistence.

---

# 14. Why SQLite?

SQLite is suitable for the current research prototype because it is:

- Lightweight
- File based
- Easy to configure
- Easy to reset during experiments
- Sufficient for local metadata storage

It avoids introducing unnecessary infrastructure during prototype
development.

For a larger multi-user deployment, a server-based relational
database such as PostgreSQL could replace SQLite.

---

# 15. Sentence Transformers

Sentence Transformers are used to convert text into semantic vector
representations.

The application uses:

```text
sentence-transformers/all-MiniLM-L6-v2
```

Both document chunks and user questions are processed using the same
model.

Example:

```text
Document Chunk
      |
      v
MiniLM
      |
      v
384-D vector
```

and:

```text
User Question
      |
      v
MiniLM
      |
      v
384-D vector
```

Because both representations are generated in the same embedding
space, semantic similarity search can be performed.

---

# 16. Why all-MiniLM-L6-v2?

The current embedding model produces 384-dimensional embeddings.

It provides a useful balance for a prototype between:

- Embedding quality
- Model size
- Local inference requirements
- Storage requirements
- Retrieval speed

It can also run locally, meaning document content does not need to be
sent to an external embedding API merely to generate vectors.

The project does not assume that this embedding model is universally
optimal.

Alternative embedding models could be evaluated in future work.

---

# 17. Why Embeddings Instead of Keyword Search?

Keyword search primarily depends on lexical matches.

For example:

```text
Document:

"Services exchange asynchronous events through Kafka."
```

A user might ask:

```text
"How do the microservices communicate?"
```

The wording is different even though the concepts are related.

Embedding-based search attempts to retrieve information according to
semantic similarity.

This makes it useful for natural-language question answering.

---

# 18. NumPy

NumPy is used for numerical vector representation and manipulation.

Generated embeddings are represented as NumPy arrays.

The application converts vectors to:

```text
float32
```

before vector indexing.

This format is compatible with the FAISS implementation used by the
project.

---

# 19. PyTorch

PyTorch is used indirectly through the Sentence Transformers stack to
execute the embedding model.

The application itself does not train a new neural network.

Instead, it performs inference using a pretrained embedding model.

This distinction is important:

```text
This project:

Pretrained model
      ↓
Embedding inference
```

rather than:

```text
Training dataset
      ↓
Neural network training
      ↓
New embedding model
```

The research contribution is centered on RAG system design and
evaluation rather than training a foundation model from scratch.

---

# 20. FAISS

FAISS is one of the vector-search implementations supported by the
project.

FAISS stands for:

```text
Facebook AI Similarity Search
```

It is designed for efficient similarity search over vector
representations.

The current implementation uses:

```text
IndexFlatIP
```

with normalized embeddings.

---

# 21. Why FAISS?

FAISS provides a useful local vector-search baseline.

Advantages include:

- Local execution
- No cloud dependency
- Fast similarity search
- Simple experimentation
- No external database required

It is particularly useful for development and controlled experiments.

The current implementation stores vector metadata separately in
SQLite.

---

# 22. Astra DB

Astra DB provides the cloud-based vector database implementation used
by the project.

The Astra collection is configured using:

```text
Dimension = 384

Metric = cosine
```

Astra stores the embedding together with metadata such as:

```text
chunk ID
document ID
filename
chunk index
chunk content
```

This allows semantic search results to contain the corresponding
chunk information directly.

---

# 23. Why Use Astra When FAISS Already Exists?

FAISS and Astra represent different vector-storage approaches.

```text
FAISS

Application
   |
   v
Local vector index
   +
SQLite metadata
```

compared with:

```text
Astra

Application
   |
   v
Cloud vector database
   |
   +-- Vector
   +-- Chunk content
   +-- Metadata
```

Supporting both provides architectural flexibility and also creates
an opportunity for experimental comparison.

Possible comparison dimensions include:

- Retrieval latency
- Result ranking
- Deployment complexity
- Persistence
- Scalability
- Metadata handling

The project should not assume that one backend is always superior.
Their behavior should be measured under defined experimental
conditions.

---

# 24. Important Similarity-Score Consideration

FAISS and Astra may expose different numerical similarity values.

During development, the same query produced similar chunk rankings
while the raw scores differed substantially.

Therefore:

```text
FAISS score 0.45
```

cannot automatically be compared directly with:

```text
Astra score 0.72
```

to conclude that Astra produced a more confident or more accurate
result.

Evaluation should instead consider:

- Whether the relevant chunk was retrieved
- Its ranking position
- Retrieval metrics such as Precision@K or Recall@K
- Downstream answer quality

# 25. Groq

Groq is currently used as the LLM inference provider.

The backend communicates with Groq through an OpenAI-compatible API
interface.

The current configured model is:

```text
openai/gpt-oss-20b
```

The LLM receives:

```text
RAG instructions
       +
Retrieved document context
       +
User question
```

and returns the generated answer.

---

# 26. Why Separate the LLM from Retrieval?

The architecture intentionally separates:

```text
Retrieval
```

from:

```text
Generation
```

The retrieval system determines:

> What project information is relevant?

The LLM determines:

> How should that information be expressed as a natural-language
> answer?

This separation allows individual components to be replaced.

For example:

```text
MiniLM
   ↓
Different embedding model
```

or:

```text
FAISS
   ↓
Astra
```

or:

```text
Current LLM
   ↓
Different LLM
```

without redesigning the complete application.

# 28. Technology Selection Principles

The stack was selected using the following general principles:

### Modularity

Components should be independently replaceable.

### Research Flexibility

Parameters and technologies should be easy to compare experimentally.

### AI Ecosystem Compatibility

The backend should integrate easily with embedding and vector-search
libraries.

### Prototype Simplicity

Infrastructure complexity should remain manageable for an academic
prototype.

### Reproducibility

The system should be capable of being configured and executed again
using documented dependencies and configuration.

# 31. Viva Questions and Answers

## Why did you choose Python for the backend?

Python provides direct access to the AI libraries required for the
project, including Sentence Transformers, PyTorch, FAISS, and NumPy.
FastAPI allows these components to be exposed through REST APIs
without introducing a separate AI service.

## Why did you choose FastAPI?

FastAPI provides a lightweight Python API framework with request
validation, type support, asynchronous capabilities, and automatic
OpenAPI documentation. It integrates naturally with the Python AI
ecosystem used by the project.

## Why did you choose MiniLM?

The current MiniLM model generates relatively compact
384-dimensional semantic embeddings and can run locally. It provides
a practical balance between computational requirements and semantic
retrieval capability for the prototype.

## Why are both FAISS and Astra used?

FAISS provides a local vector-search implementation, while Astra
provides a cloud vector-database implementation. Supporting both
demonstrates vector-store abstraction and enables controlled
comparison of retrieval behavior and performance.

## Why do you still need SQLite?

SQLite stores application metadata about uploaded documents and
chunks. FAISS primarily stores vectors, while SQLite provides the
metadata mapping required by the local FAISS implementation.

## Is Astra replacing SQLite?

Not completely in the current architecture. Astra stores vectors and
retrieval metadata, while SQLite remains the application's document
metadata database.

## Why use an LLM after vector search?

Vector search retrieves relevant information but does not itself
produce a complete natural-language answer. The LLM uses the
retrieved information to synthesize a response to the user's
question.

## Are you training your own LLM?

No. The project uses pretrained embedding and language models. The
research focuses on Retrieval-Augmented Generation architecture,
retrieval behavior, grounding, and evaluation rather than training a
foundation model.
