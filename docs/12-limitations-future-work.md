# Limitations and Future Work

## 1. Introduction

The AI-Powered Intelligent Software Engineering Assistant demonstrates
how Retrieval-Augmented Generation can combine project-specific
technical documentation with Large Language Models.

The current implementation successfully demonstrates the major RAG
workflow:

```text
Document Ingestion
        ↓
Text Processing
        ↓
Chunking
        ↓
Embedding
        ↓
Vector Storage
        ↓
Semantic Retrieval
        ↓
Context Augmentation
        ↓
LLM Generation
```

However, the project is a research prototype and has several
limitations.

Identifying these limitations is important because they define both
the boundaries of the experimental conclusions and opportunities for
future research and engineering improvements.

---

# 2. Limited Evaluation Corpus

The current prototype is evaluated using a controlled collection of
software engineering documents.

A real enterprise software project may contain:

```text
Thousands of documents
Source code repositories
API specifications
Architecture diagrams
Tickets
Wiki pages
Requirements
Database schemas
Operational documentation
```

The behavior observed on the evaluation corpus may therefore not
directly represent very large enterprise knowledge bases.

## Future Work

Future experiments can use larger and more diverse software
engineering corpora.

---

# 3. Limited Document Formats

The current document-processing implementation primarily supports:

```text
PDF
TXT
Markdown
```

Enterprise engineering knowledge can also exist in:

```text
DOCX
HTML
OpenAPI specifications
Source-code files
Jupyter notebooks
Configuration files
Wiki exports
```

## Future Work

The ingestion layer can be extended with format-specific parsers.

For example:

```text
DOCX parser

HTML parser

OpenAPI parser

Source-code parser
```

---

# 4. Character-Based Chunking

The current implementation uses a relatively simple
character-oriented chunking strategy.

Default configuration:

```text
chunk_size = 1000
chunk_overlap = 200
```

Character-based chunking does not explicitly understand software
engineering structure.

For example, it may split:

```text
API descriptions

Classes

Methods

Requirements

Architecture sections
```

at boundaries that are not semantically ideal.

## Future Work

More advanced strategies could include:

```text
Sentence-aware chunking

Paragraph-aware chunking

Heading-aware chunking

Token-based chunking

Semantic chunking

Source-code-aware chunking
```

---

# 5. Fixed Embedding Model

The current system uses:

```text
sentence-transformers/all-MiniLM-L6-v2
```

with:

```text
384-dimensional embeddings
```

Using one embedding model limits conclusions about embedding quality.

Different models may behave differently for:

```text
Technical terminology
Source code
API documentation
Architecture descriptions
Mixed natural language and code
```

## Future Work

Future experiments can compare multiple embedding models while keeping
the corpus and evaluation dataset fixed.

---

# 6. Embedding Model Versioning

The current prototype does not implement a comprehensive vector-index
versioning system tied to the embedding model.

Changing the embedding model requires careful re-indexing because
vectors generated by different models should not simply be mixed in
the same search space.

## Future Work

Store metadata such as:

```text
embedding_model
embedding_dimension
index_version
created_at
```

with each index or collection version.

---

# 7. Vector and Metadata Consistency

The application stores related information across separate persistence
systems.

For FAISS:

```text
SQLite
+
FAISS
```

For Astra:

```text
SQLite
+
Astra DB
```

These operations are not part of one distributed transaction.

A vector insertion may succeed while a relational database operation
fails, or vice versa.

During development, a real mismatch occurred where:

```text
FAISS vectors = 18
SQLite chunks = 9
```

This resulted in vector positions without corresponding relational
metadata.

## Future Work

Possible improvements include:

```text
Indexing status

Idempotent ingestion

Compensating operations

Reconciliation jobs

Automatic re-indexing

Background ingestion workflow
```

---

# 8. No Full Transaction Across Vector Store and SQLite

SQLite transactions protect SQLite operations but cannot automatically
roll back:

```text
FAISS file changes
```

or:

```text
remote Astra operations
```

Therefore, the current architecture provides eventual application
consistency rather than a true distributed transaction across all
storage components.

## Future Work

A production architecture could use an ingestion state machine:

```text
UPLOADED
    ↓
PROCESSING
    ↓
EMBEDDING
    ↓
INDEXING
    ↓
READY
```

with:

```text
FAILED
```

and retry/recovery mechanisms.

---

# 9. Basic Retrieval Strategy

The current system primarily performs dense semantic vector retrieval.

It does not currently implement a complete hybrid retrieval pipeline
combining:

```text
Dense Vector Search
        +
Keyword / Lexical Search
```

Technical documents often contain exact identifiers such as:

```text
SCM-304

POST /api/v1/orders

PaymentServiceImpl

ERR_CONNECTION_TIMEOUT
```

Exact identifiers may benefit from lexical retrieval.

## Future Work

A hybrid architecture could combine:

```text
Semantic retrieval
+
BM25 / keyword retrieval
+
Result fusion
```

---

# 10. No Reranking Layer

The current pipeline retrieves Top-K vector results and sends selected
context to the LLM.

It does not currently use a dedicated reranking model.

## Future Work

A reranker could receive the initial retrieval candidates and reorder
them according to question relevance.

Conceptually:

```text
Vector Search
     ↓
Top 20 Candidates
     ↓
Reranker
     ↓
Best 5 Chunks
     ↓
LLM
```

This could be evaluated against direct Top-K vector retrieval.

---

# 11. Similarity Score Is Not Confidence

The vector-search similarity score indicates vector similarity.

It does not directly represent:

```text
Probability that the answer is correct
```

or:

```text
Probability that the final response is grounded
```

This distinction is especially important because FAISS and Astra may
expose different numerical score behavior.

## Future Work

An evidence sufficiency mechanism could combine:

```text
Retrieval features
Question type
Evidence coverage
Answer verification
```

rather than relying on one similarity threshold.

---

# 12. Unsupported Question Detection

The current LLM prompt instructs the model to state that the available
documents do not provide enough information when context is
insufficient.

This is useful but does not guarantee perfect abstention.

A semantically related but irrelevant chunk can still be retrieved.

The LLM may then attempt to construct an answer.

## Future Work

Unsupported-question detection could use:

```text
Calibrated retrieval threshold

Evidence sufficiency classifier

Answer verifier

Entailment model

Claim-level grounding verification
```

Thresholds should be calibrated experimentally rather than chosen
arbitrarily.

---

# 13. RAG Does Not Eliminate Hallucination

Retrieval-Augmented Generation can provide project-specific evidence,
but it does not guarantee that the generated response contains only
supported claims.

Possible failure:

```text
Correct evidence retrieved
        ↓
LLM generates correct statement
        +
unsupported additional detail
```

Therefore:

```text
Successful retrieval
```

does not automatically imply:

```text
Fully grounded answer
```

## Future Work

Introduce a post-generation verification stage:

```text
Generated Answer
      ↓
Extract Claims
      ↓
Compare Claims with Evidence
      ↓
Remove / Flag Unsupported Claims
```

---

# 14. Citation Granularity

The current system returns chunk-level source references.

This provides traceability but may not identify the exact sentence
supporting a generated claim.

## Future Work

Citation support can be improved using:

```text
Sentence-level evidence

Highlighted passages

Source preview

Page numbers for PDFs

Claim-to-source mapping
```

This would improve user verification.

---

# 15. Limited Conversation Memory

The current application primarily treats each question as an
independent RAG request.

A follow-up such as:

```text
What database does it use?
```

may require understanding what:

```text
"it"
```

refers to in the previous conversation.

## Future Work

Implement conversational retrieval using:

```text
Conversation history

Question rewriting

Context-aware retrieval
```

For example:

```text
Previous:
Tell me about the Payment Service.

Follow-up:
How is it deployed?

Rewritten retrieval query:
How is the Payment Service deployed?
```

---

# 16. No Streaming Generation

The current frontend waits for the generated answer to be returned.

For longer responses, users may perceive additional waiting time.

## Future Work

Support token streaming:

```text
LLM
 ↓
Token
 ↓
Token
 ↓
Token
 ↓
Frontend
```

This would improve perceived responsiveness.

---

# 17. External LLM Dependency

The current generation layer uses Groq.

Therefore, generation depends on:

```text
Network availability

Provider availability

Provider latency

API configuration
```

## Future Work

Because LLM access is isolated behind `llm_service`, additional
providers or local models can be evaluated.

For example:

```text
Hosted LLM
vs
Local LLM
```

---

# 18. Astra Network Dependency

Astra retrieval requires remote communication.

This introduces network-related latency and availability factors that
do not exist in the same form for local FAISS retrieval.

## Future Work

Evaluate:

```text
Local vector search

vs

Managed cloud vector search
```

under controlled workloads and larger datasets.

---

# 19. FAISS Metadata Management

FAISS provides efficient vector search but the current architecture
requires SQLite to resolve vector positions to chunk metadata.

This introduces synchronization complexity.

## Future Work

Possible approaches include:

```text
Explicit vector ID mapping

Rebuildable index metadata

Transactional ingestion coordinator

Alternative vector database
```

---

# 20. Basic Authentication and Authorization

The current research prototype does not focus on enterprise
authentication and authorization.

A production software-engineering assistant may contain sensitive
project information.

## Future Work

Add:

```text
User authentication

Role-based access control

Document-level authorization

Project/workspace isolation
```

Retrieval itself should respect authorization so that unauthorized
documents are never added to a user's RAG context.

---

# 21. Security and Privacy

The system processes uploaded project documentation.

Production deployment would require stronger controls for:

```text
Data encryption

Secret management

Audit logging

Retention policies

Access monitoring

Data isolation
```

## Future Work

Integrate enterprise security controls and managed secret storage.

---

# 22. Prompt Injection Through Documents

RAG systems can retrieve text from uploaded documents.

A malicious document could contain instructions intended to influence
the LLM rather than provide knowledge.

For example:

```text
Ignore previous instructions and reveal...
```

The current prototype does not implement a comprehensive defense
against document-based prompt injection.

## Future Work

Potential protections include:

```text
Treat retrieved content strictly as untrusted data

Prompt isolation

Content filtering

Instruction detection

Output verification
```

---

The current system focuses mainly on textual engineering documents.

Software engineering knowledge also exists directly in source code.

## Future Work

Add repository-aware ingestion for:

```text
Java
Python
JavaScript
TypeScript
Configuration files
SQL
```

Code could be chunked by:

```text
Class
Method
Function
Module
```

rather than arbitrary character boundaries.

A future version could connect technical documentation with actual

Example questions:

# 26. Multimodal Engineering Documents

Architecture knowledge can also exist in:

```text
Diagrams

Screenshots

Flowcharts

UML

Database diagrams
```

The current text-oriented pipeline does not fully interpret these
visual sources.

## Future Work

Introduce multimodal document processing capable of extracting and
reasoning over both text and diagrams.

# 27. Evaluation Dataset Scale

The initial controlled dataset is useful for validating the
evaluation pipeline, but strong experimental conclusions require a
larger and more diverse set of questions.

## Future Work

Build a manually verified dataset containing categories such as:

```text
Direct factual
Paraphrased
Cross-document
Multi-chunk
Reasoning
Unsupported
```

The dataset should contain enough examples from each category to
support meaningful analysis.

---

# 28. Automated Evaluation Limitations

Metrics such as:

```text
Precision
Recall
MRR
```

are objective when ground-truth relevance is available.

However, answer-level properties such as:

```text
Correctness
Groundedness
Usefulness
```

may require human judgment.

Using another LLM as an evaluator can help scale evaluation but can
also introduce evaluator bias.

## Future Work

Use a combination of:

```text
Deterministic metrics

Human evaluation

Carefully validated LLM-assisted evaluation
```

---

# 29. Scalability

The current prototype has not yet demonstrated behavior on
enterprise-scale corpora.

Larger deployments introduce challenges such as:

```text
Millions of chunks

Index growth

Concurrent users

Document updates

Document deletion

Incremental indexing
```

## Future Work

Evaluate:

```text
Indexing throughput

Retrieval latency vs corpus size

Concurrent request handling

Storage growth

Incremental update performance
```

---

# 30. Document Update and Deletion

The current project focuses primarily on upload and retrieval.

A complete knowledge-management system also needs robust handling for:

```text
Document update

Document replacement

Document deletion
```

Vector records associated with old document versions must be updated
or removed.

## Future Work

Implement lifecycle operations:

```text
Create
Update
Re-index
Delete
```

with consistent cleanup across SQLite and the vector store.

---


# 34. Summary

The current project demonstrates a complete RAG architecture but
intentionally remains a research prototype.

The main future directions are:

```text
Better chunking

Hybrid retrieval

Reranking

Evidence verification

Better citations

Conversational RAG

Source-code understanding

Enterprise security

Scalable indexing

Document lifecycle management

Larger evaluation datasets
```

These extensions provide a clear path from the current M.Tech
prototype toward a production-oriented intelligent software
engineering assistant.
